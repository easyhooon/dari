---
title: Gradle Plugin
description: Capture bridge messages from a one-time mapping, without Dari calls in your bridge code
---

The Dari Gradle plugin records bridge traffic without per-call code. You tell it once where your bridge receives requests and where it sends responses. In debug builds it then inserts the same `DariInterceptor` calls you would otherwise write by hand.

Everything after capture stays the same: storage, the in-app inspector, the desktop app, export and masking.

The plugin is optional. Calling the interceptor yourself, as in [Setup](./setup), remains the default and keeps working, and both can live in one app.

## Where each piece goes

| File | What to put there |
| --- | --- |
| `app/build.gradle.kts` `dependencies { }` | `dari` / `dari-noop`, the same as for the manual way. The plugin doesn't add them. |
| `settings.gradle.kts` | `mavenCentral()` in `pluginManagement { repositories { } }`, so Gradle can find the plugin. |
| `app/build.gradle.kts` (the module that adds `dari` / `dari-noop`) | `id("io.github.easyhooon.dari")` in `plugins { }`, and the `dari { }` mapping block. |
| Your `Application.onCreate()` | `Dari.setProtobufDecoder(...)`, only if you capture protobuf payloads. |
| Your bridge code | Nothing. |

The dependencies alone don't turn this on: without the plugin and `dari { }`, nothing changes. Don't put `dari { }` in the root `build.gradle.kts`. A bridge in another module needs the plugin and its own `dari { }` in that module's `build.gradle.kts`.

## Background

### Library vs plugin

A **library** (`implementation`, `api`) is code that ships in your APK and runs on the device. `dari` is a library. It can record messages, but it cannot change your code, so your bridge has to call it.

A **Gradle plugin** (`plugins { id(...) }`) is code that runs inside Gradle on your machine or CI while the app builds. It is not packaged into the APK. AGP (`com.android.application`), KSP and the Sentry Android Gradle Plugin are all plugins.

```text
Build (your machine or CI, inside Gradle)
  plugins { ... }        plugins load and configure the build
  compile                your code -> .class files
  transform              the Dari plugin rewrites the compiled classes   <- here
  dex + package          classes and libraries -> APK

Runtime (device)
  your app               dari records what the inserted calls report
```

Inserting calls into your code needs a plugin. Recording and showing messages is the library's job, so the plugin needs `dari` too.

### What is a DSL?

A DSL (domain-specific language) is a small language for one job. Gradle build scripts use Kotlin (or Groovy) to build one: `android { }`, `dependencies { }` and `plugins { }` are all ordinary Kotlin function calls that take a block.

The plugin adds one more block, `dari { }`. Inside it, `webToAppRequest(...) { handlerName = arg(0) }` is plain Kotlin as well:

- `webToAppRequest` is a function on the `dari` extension;
- `handlerName` is a property;
- `arg(0)` returns a value that describes "the first parameter".

Nothing runs on the device at this point. The block only records a description that the plugin bakes into your classes.

### What is ASM?

Kotlin and Java compile to JVM bytecode: `.class` files that hold a list of instructions per method. Android turns them into DEX afterwards.

[ASM](https://asm.ow2.io/) is the standard library for reading and rewriting that bytecode. AGP exposes it through its instrumentation API: a plugin registers an `AsmClassVisitorFactory`, and AGP passes every class through it before dexing. This is also how Firebase Performance, Sentry and Hilt modify compiled code.

For a mapped method such as:

```kotlin
fun onBridgeRequest(handlerName: String, requestId: String, data: String?) {
    when (handlerName) { /* ... */ }
}
```

the plugin adds one call at the very start of the method body in the compiled class. In source terms the result looks like this (your `.kt` file is not changed):

```kotlin
fun onBridgeRequest(handlerName: String, requestId: String, data: String?) {
    DariHooks.onMappedCall("""{"kind":"WEB_TO_APP_REQUEST","fields":{...}}""", this, arrayOf(handlerName, requestId, data))
    when (handlerName) { /* ... */ }
}
```

On the device, `DariHooks` (inside `dari`) reads the mapping, picks the values out of the arguments and calls `onWebToAppRequest(...)` on an interceptor. Because the plugin works on bytecode, it handles Java and Kotlin the same way.

The plugin also rewrites two more things:

- **`webView.addJavascriptInterface(bridge, name)` calls** now go through `DariHooks`. Dari can then tell which WebView a bridge object belongs to.
- **`WebViewClient.doUpdateVisitedHistory` overrides** now report the page URL.

## Setup

```kotlin
// settings.gradle.kts
pluginManagement {
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
}
```

```kotlin
// app/build.gradle.kts
plugins {
    id("com.android.application")
    id("io.github.easyhooon.dari") version "{{DARI_VERSION}}"
}

dependencies {
    debugImplementation("io.github.easyhooon:dari:{{DARI_VERSION}}")
    releaseImplementation("io.github.easyhooon:dari-noop:{{DARI_VERSION}}")
}

dari {
    webToAppRequest("com.example.MainActivity.BridgeInterface", "onBridgeRequest") {
        handlerName = arg(0)
        requestId = arg(1)
        data = arg(2)
    }
    webToAppResponse("com.example.MainActivity", "sendResponseToWeb") {
        handlerName = arg(0)
        requestId = arg(1)
        success = arg(2)
        data = arg(3)
    }
}
```

Use the same version for the plugin, `dari` and `dari-noop`.

The mapping works best when your bridge has one request entry point and one response sender. The [interceptor guide](./interceptor) recommends that layout for manual logging too.

## Mapping reference

### Where

| Function | Map it to | Becomes |
| --- | --- | --- |
| `webToAppRequest(class, method)` | the method JavaScript calls (`@JavascriptInterface`) | `onWebToAppRequest` |
| `webToAppResponse(class, method)` | the method that sends the result back to the page | `onWebToAppResponse` |
| `appToWebRequest(class, method)` | the method that calls into the page | `onAppToWebRequest` |
| `appToWebResponse(class, method)` | the method the page calls with its answer | `onAppToWebResponse` |

- `class` is the fully qualified class name. Nested classes may use `.` or `$`.
- `method` is the method name. Every overload with that name is mapped.
- The hook runs when the method starts, before its body.
- `suspend` functions work too. A suspend function is called again each time it resumes; only the first call is recorded. `--info` shows `(suspend; resumptions skipped)` next to the method.

### Fields

| Field | Used by | Notes |
| --- | --- | --- |
| `handlerName` | requests (required), `webToAppResponse` | Responses fall back to the request's name. |
| `requestId` | all; required for responses | Pairs a response with its request. |
| `data` | all | Text is stored as is. Bytes (from `base64(...)` or a `ByteArray` parameter) go through the protobuf API. |
| `displayName` | requests | Same as the manual `displayName` overload. |
| `success` | responses | Leave it out for "always SUCCESS". `false`, `"false"` or `0` record ERROR. |
| `fireAndForget` | requests | `true` resolves the entry at once. `false` defers to `DariConfig.fireAndForget`, like passing `null` by hand. |
| `onlyIf` | all | Records the call only when `true`. A missing value (`null`) counts as `false`. For one method that carries several kinds of message. |
| `tag` | all | Overrides `dari { tag }` for this mapping. |

### Expressions

| Expression | Value |
| --- | --- |
| `arg(n)` | The method's `n`th parameter, starting at 0 (`this` doesn't count). |
| `constant("x")`, `constant(true)` | A fixed value. |
| `json(expr, "a.b.0")` | A field from a JSON string, a JSON object such as kotlinx.serialization's `JsonObject` or Gson's `JsonObject` (anything whose `toString()` is JSON), or a nested `json(...)`. A value that isn't JSON yields `null`. |
| `base64(expr)` | Base64 text decoded to bytes. |
| `expr.equalsTo("x")` | `true` when the value's text equals `"x"`. |
| `isNull(expr)` | `true` when the value is `null`, e.g. a missing `error` field. |

### Options

```kotlin
dari {
    tag = "Checkout"                         // default: the name passed to addJavascriptInterface
    scope = InstrumentationScope.ALL         // default: InstrumentationScope.PROJECT
}
```

`InstrumentationScope` comes from `com.android.build.api.instrumentation`.

## Recipes

### One JSON string per call

Many bridges pass one JSON string, e.g. `Android.postMessage('{"action":"login","id":"7","params":{...}}')`:

```kotlin
dari {
    webToAppRequest("com.example.WebBridge", "postMessage") {
        handlerName = json(arg(0), "action")
        requestId = json(arg(0), "id")
        data = json(arg(0), "params")
    }
    webToAppResponse("com.example.WebBridge", "reply") {
        requestId = json(arg(0), "id")
        success = isNull(json(arg(0), "error"))
        data = arg(0)
    }
}
```

### Fire-and-forget

```kotlin
webToAppRequest("com.example.MainActivity.BridgeInterface", "onBridgeRequestFireAndForget") {
    handlerName = arg(0)
    data = arg(1)
    fireAndForget = constant(true)
}

// Only some handlers on a shared entry point:
webToAppRequest("com.example.MainActivity.BridgeInterface", "onBridgeRequest") {
    handlerName = arg(0)
    requestId = arg(1)
    data = arg(2)
    fireAndForget = arg(0).equalsTo("logEvent")
}
```

### Protocol Buffers

Map the payload to bytes, and register the decoder once at app start. Interceptors that the plugin creates use it.

```kotlin
webToAppRequest("com.example.MainActivity.BridgeInterface", "onProtobufBridgeRequest") {
    handlerName = constant("protobufGreeting")
    requestId = arg(0)
    data = base64(arg(1))
}
```

```kotlin
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        Dari.setProtobufDecoder(protobufDecoder { /* see Protocol Buffers */ })
    }
}
```

`Dari.setProtobufDecoder` is a no-op in `dari-noop`. See [Protocol Buffers](./protobuf) for writing the decoder.

### App to Web

```kotlin
appToWebRequest("com.example.MainActivity", "sendToWeb") {
    handlerName = arg(0)
    requestId = arg(1)
    data = arg(2)
    fireAndForget = isNull(arg(1))           // no requestId: the page won't answer
}
appToWebResponse("com.example.MainActivity.BridgeInterface", "onAppToWebResponse") {
    requestId = arg(0)
    success = arg(1)
    data = arg(2)
}
```

### Requests and responses through one method

When one method sends both, e.g. a `type` field of `"request"` or `"response"`, map it twice and filter each mapping with `onlyIf`:

```kotlin
appToWebRequest("com.example.WebBridge", "postMessage") {
    handlerName = json(arg(0), "action")
    requestId = json(arg(0), "id")
    onlyIf = json(arg(0), "type").equalsTo("request")
}
appToWebResponse("com.example.WebBridge", "postMessage") {
    requestId = json(arg(0), "id")
    data = arg(0)
    onlyIf = json(arg(0), "type").equalsTo("response")
}
```

## What else is captured

- **Tag per WebView.** Each WebView gets its own interceptor. The tag is the name passed to `addJavascriptInterface` (`Android`), unless you set `tag`.
  - Requests use the WebView their bridge object was added to.
  - Responses use the interceptor that recorded the matching request.
  - Mapped methods that are not bridge objects use a `WebView` parameter if there is one, otherwise the WebView seen most recently.
- **Page URL.** Taken from `doUpdateVisitedHistory`, so redirects, link clicks and SPA history changes count too. This needs a `WebViewClient` subclass that overrides `doUpdateVisitedHistory`; an empty override is enough.

## Rules

- **Debug only.** Only debuggable variants are instrumented. Release builds contain no hooks.
- **`dari-noop` is safe.** It ships pass-through hooks, so a debuggable variant built against `dari-noop` runs normally and records nothing.
- **Scope.** By default only the module's own classes are rewritten.
  - A bridge inside a third-party AAR needs `scope = InstrumentationScope.ALL`. That re-dexes every AAR in the app; a cold build took about 5 minutes longer in testing.
  - A bridge in another module of your project needs the plugin applied in that module.
- **Manual logging still works.** The plugin only touches mapped methods. If a mapped method already calls `DariInterceptor`, the plugin skips that method and prints a build warning. It checks only that method's own body: a manual call elsewhere on the same path, such as in a handler, is recorded a second time. Use one way per bridge.
- **Build warnings.** A mapped class without the named method prints a warning. A misspelled class name matches nothing and prints nothing, so check the inspector after the first run.
  - Warnings only appear when the class is rebuilt.
  - To list what was rewritten, run with `--info` and look for `Dari: instrumented`.
- **Not covered.**
  - Calls made through reflection.
  - `androidx.webkit` message channels (`addWebMessageListener`, `WebMessagePort`).
  - Values computed inside the method body. Only the method's parameters can be mapped.
  - The re-entries a `suspend` function receives when it resumes (with `null` arguments). Only the first call is recorded.
